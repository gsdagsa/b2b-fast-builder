# 账号与域名接入

用于第一次正式上线：确认客户自己的 Hostinger VPS 与 Resend 账号、把网站域名解析到 VPS、验证发信域名并安全保存 API Key。界面、权限名和命令会变化，执行时重新读取 Hostinger 与 Resend 官方文档。

面向小白的主动触发、缺失工具安装、逐轮话术与续接规则见 [主动引导上线](guided-launch.md)。本文件是 Agent 的技术清单，不要整篇发给客户。

仅在当前任务实际需要部署、DNS 或发信接入时使用。不要把下面的注册步骤变成设计前置条件；默认先做样板、确认样式并主动收集客户真实资料，再按需接通服务。

## 1. 默认决策

极速建站默认采用：

```text
域名继续在原注册商续费
        ↓
DNS 留在原注册商或现有 DNS 提供商
        ↓
添加 A/AAAA 记录指向 VPS IP
        ↓
Resend 的验证记录也写入同一个 DNS 平台
```

VPS 方案不需要迁移 Nameserver，也不要求域名进入某个特定托管商的 Zone。客户仍在原购买平台拥有并续费域名，DNS 变更只增加或修改指向记录。

以下情况不要强制修改整站 DNS：

- 客户有 IT 团队、企业级 DNS、复杂邮件系统或合规限制。
- 只能发布一个子域名，且现有 DNS 提供商允许添加指向 VPS 的 A 记录。
- 用户明确要求保留现有权威 DNS。
- 现有记录已在 Cloudflare 或其他代理服务后面：按其现有平台的记录规则添加，不要求迁出。

多台 VPS 或使用负载均衡时，用 A 记录指向入口 IP 或按服务商文档配置；不要把同一站点的解析指向多台配置不一致的服务器。

## 2. 客户看到的四步

以下四项是接入阶段的概览，不是建站开场任务或必须连续执行的向导。每次只展示当前依赖的一项；先复用已有账号和资料：

1. **告诉我网站地址。** 输入域名、在哪里买的，以及接收询盘的邮箱。
2. **确认 VPS 访问。** Agent 打开 hPanel 官方入口，客户在面板创建 VPS、设置系统并注入 SSH 密钥；客户完成后回来回复“已配置”。网页登录本身不代表服务器已可部署。
3. **让域名指向新网站。** Agent 核对旧网站和企业邮箱，确认后给出要添加的 A/AAAA 记录和 DNS 平台入口；客户按指引保存后回复“已修改”，Agent 自己检查。
4. **连接询盘邮件。** 注册 Resend，验证发信域名，再创建限定权限的发送密钥并安全保存。每轮只做当前一步，客户只回传普通资料、脱敏状态或“已保存”。

其余动作由 Agent 完成，并用“检查中、已完成、需要你操作”三个状态反馈。默认隐藏 DNS、MX、DKIM、数据库等术语；需要客户操作时，既显示页面上的真实字段名，也用一句白话解释用途。

按 [客户接入表单模板](../assets/onboarding-intake.example.yaml) 收集信息。能从仓库、公开 DNS、VPS 或已授权环境读取的字段，不重复向客户提问。

## 3. 输入框与授权边界

可以进入普通对话框或表单：

- 网站域名和购买平台名称。
- 接收询盘的邮箱。
- 是否正在使用企业邮箱、旧网站和其他子域名。
- 原 DNS 导出文件、公开记录列表或解析页面截图。
- 公司名称、发件人显示名称等非敏感设置。

只能进入实际可用的安全渠道（SSH 密钥注入、系统凭据存储或经核实不进入对话/日志的专用输入）：

- Resend API Key。
- SSH 私钥 passphrase。
- 域名注册商或 DNS 平台的 API Token。

不能收集到聊天或普通表单：

- 账号密码、短信验证码、双重验证代码。
- VPS root 密码、SSH 私钥本体、恢复码和浏览器 Cookie。

普通聊天不是安全输入框，HTML 密码掩码也不能证明数据不会进入会话或日志。只有确认能直接写入目标 Secret/安全存储且不回显时才能使用；不得通过让用户“发我 Key”再由 Agent 复制实现。宿主不支持时，默认引导用户在官方控制台保存，回来只说“已保存”。安全输入期间不截图、不读取剪贴板或表单值，不把 Secret 插入 shell 命令参数/工具调用文本。

用户误发密钥时不复述、不存入进度文件，提醒去发行平台撤销并重建，再走安全路径。SSH 私钥暴露时立即在服务器和 hPanel 撤销对应公钥。不要声称能够从聊天历史中彻底删除已暴露凭据。

## 4. 账号归属

- Hostinger、Resend、域名注册商和 Git 仓库默认都属于客户。
- 用户自己完成注册、登录、服务条款、套餐选择、付费确认和双重验证。
- Agent 可以打开正确页面、检查状态并在授权后配置资源，但不能代替用户拥有账号。
- 不让用户把 API Key、SSH 密码或注册商密码粘贴到聊天；优先使用密钥注入、CLI 安全输入或平台安全存储。

## 5. 把现有域名解析到 VPS

按以下顺序执行，不能跳过 DNS 盘点：

1. 客户确认 VPS 已创建，操作系统就绪，Agent 获得 SSH 访问。
2. 导出并核对现有 DNS 记录，至少覆盖 A、AAAA、CNAME、MX、TXT、CAA、SRV、DKIM、DMARC 和各类平台验证记录。自动扫描只能作为起点，不能当作完整备份。
3. 在现有 DNS 平台添加或修改 A/AAAA 记录，把根域名和 `www` 指向 VPS IP；这一步只有在 DNS 平台 API 已单独授权时才能由 Agent 自动完成。
4. 保留企业邮箱和验证记录不动；确认没有记录被覆盖或删除。
5. 等 DNS 记录生效，用 `dig`/`nslookup` 验证解析指向正确的 IP。
6. 在 VPS 上配置 Nginx 站点并签发 SSL 证书（certbot），绑定根域名和 `www`，选定一个 canonical host 并重定向另一个。
7. 逐项验证网站、企业邮箱和关键子域名不受影响。

修改生产 DNS 记录属于生产变更。执行前保存旧记录、完整 DNS 导出和回滚步骤；目标域名不清楚时停止。

## 6. Resend 小白接入流程

### 用户必须完成

1. 在 Resend 注册或登录自己的账号。
2. 确认真实收件邮箱，即网站询盘最终通知到哪里。
3. 在 Resend 的 Domains 页面添加一个客户拥有的发信域名。默认优先使用专用子域，例如 `notify.example.com`，把网站询盘邮件与其他邮件信誉隔离。只配置 Sending，不因“接收询盘通知”启用 Receiving 或替换企业邮箱的根域 MX；Resend 是发出通知，实际接收仍用客户原邮箱。
4. 按 Resend 返回的记录清单，把 SPF、DKIM（和按需的 DMARC）验证记录加到域名实际所在的 DNS 平台；DNS 平台支持一键授权时，用户在官方页面确认即可。
5. 等待发信状态变为 Verified。自动验证失败时，再逐条核对 Resend 返回的记录；DMARC 在基础验证后按业务策略补充。
6. 先确定安全保存渠道，再创建生产 API Key：Agent 给出项目名加环境名，权限选择 **Sending access**，并限制到刚验证的发信域名。Key 只显示一次。登录 Resend 不是给 Agent API 授权；不要求所有用户额外安装或登录 Resend CLI。
7. 默认把 Key 保存到 VPS 上 API 服务的专属环境文件（例如 `/srv/data/<site>/env/inquiry-api.env`，名称 `RESEND_API_KEY`，权限 `0600`、归属服务用户）；入口和路径以项目配置为准。用户只回“已保存”。若宿主有不进对话/日志的安全输入，则由 Agent 直接写入。
8. 确认发件人名称、From 地址和收件地址。Resend 验证域名后不要求额外创建 sender，但 From 必须使用已验证域名；建议使用真实可接收回复的地址。

### Agent 接着完成

1. 在 Node.js API 服务中读取 `RESEND_API_KEY`，配置 `FROM_EMAIL`、`TO_EMAIL` 和经过校验的 `Reply-To`。
2. 发件地址可使用 `Website Inquiry <lead@notify.example.com>`；访客邮箱只作为经过校验的 Reply-To，不能作为 From。
3. 核对生产环境的环境文件与数据库连接；保存 Secret 后重启服务，再发送测试询盘。确认数据库先入库、Resend 返回发送 ID、真实收件箱收到邮件、回复目标正确，并完成 `/thank-you/` 跳转。发送成功不等于进了用户收件箱，必须让用户回读。
4. 记录发信域名、Key 名称和环境文件路径，不记录 Key 的值。

Resend 默认测试域只能把测试邮件发到该 Resend 账号自己的邮箱。正式向其他收件人发信前，必须验证客户自己的域名并把 From 改为该域名。

如遇账号待审核、发送限制或域名未验证，记录实际状态并给出一个下一步，不自动买套餐或反复试发。域名验证见 [Resend 官方域名验证指南](https://resend.com/docs/knowledge-base/resend-domain-verification)；密钥权限见 [创建 API Key](https://resend.com/docs/api-reference/api-keys/create-api-key)。

## 7. 自动化边界

用户完成一次身份与所有权确认后，Agent 可以自动：

- 通过 SSH 连接 VPS，安装站点依赖并配置 Nginx、systemd 服务和 SSL 证书。
- 通过已授权的 DNS 平台 API 或受控 IaC 写入 A/AAAA、Resend、DKIM、SPF、DMARC 和其他 DNS 记录。
- 触发并检查 Resend 域名验证、保存服务器 Secret、部署网站并运行 smoke test。
- 生成客户只需操作一次的 DNS 记录清单和核对说明。
- 根据客户提供的 DNS 导出或截图整理记录，先生成变更预览，经确认后再写入 DNS 平台。

需要的授权按最小权限拆分：SSH 使用专用部署用户；DNS 记录使用目标 Zone 的 DNS Write/Read 或等效 API 权限。

Agent 不能在没有额外授权时自动：

- 注册 Hostinger 或 Resend 账号、接受条款或购买套餐。
- 登录任意域名注册商并修改 DNS 记录。
- 创建第一个可管理 Resend 账号资源的凭据。若用 Resend API 自动创建域名，仍需已有的全权限凭据；完成初始化后应撤销临时全权限 Key，运行时只保留域名受限的 Sending access Key。
- 猜测并覆盖现有 DNS、删除旧邮件记录或更改真实收件地址。
- 在生产服务器执行删除数据库、清空媒体目录等破坏性操作。

需要 Resend CLI 时，安装和操作按 [官方 CLI 文档](https://resend.com/docs/cli)。`resend login` 接收已创建的 API Key，并非浏览器注册或 OAuth；命令/存储后端存在版本差异，检查实际版本和凭据存储，不能把带 `0600` 权限的明文文件说成加密存储。不要将 Key 放入 `--key`/`--api-key` 参数，也不因 Sending access 无权列出域名就误判不能发信或自动改为 Full access。管理凭据仅用于已授权的初始化，运行时仍只保留域名受限的发送 Key。

## 8. 用户交互策略

按“能自动就自动，不能自动才引导”的顺序处理：

1. Agent 先读取现状并自动填充已知信息。
2. 缺少普通资料时，一次只问 1—3 个问题；有真实表单就用表单，没有就普通对话，不虚构输入组件。
3. 需要登录时直接打开官方页面；没有浏览器能力就给可点击链接和当前一步，不让客户自己寻找菜单。
4. 需要客户在 DNS 平台操作时，提供平台对应入口、要复制的记录内容及完成后应回复的词。
5. 自动化前先展示“将保留什么、将修改什么”；生产 DNS 写入和服务器配置变更必须获得明确确认。
6. 完成后只显示业务结果：网站已打开、询盘已保存、邮件已收到、域名已生效。技术详情折叠展示，供排错和交接使用。

不要要求小白执行终端命令、理解记录类型或在多个控制台来回复制。只有自动化接口不可用时，才退回截图式逐步引导。

## 9. 上线门禁

以下条件全部满足才算账号与域名接入完成：

- 账号、域名、仓库和生产资源归属已记录且由客户控制。
- 域名解析已生效且指向正确的 VPS IP；已选域名、HTTPS 与 canonical host 正常，`www` 仅在项目包含它时验收。
- 原有企业邮箱和关键 DNS 记录在记录修改后仍正常。
- Resend 发信域名为 Verified，运行时 Key 是域名受限的 Sending access。
- `RESEND_API_KEY` 只存在于服务器环境文件或等效安全存储，Git 与前端 bundle 中不存在。
- 一条真实测试询盘完成数据库、邮件、感谢页和转化事件闭环。
- 旧 DNS 记录导出、回滚方法和后续责任人已经交接。
